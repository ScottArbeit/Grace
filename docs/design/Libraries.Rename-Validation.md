# Explicit Library file rename validation

Issue #1073 implements LIB-012 through LIB-014 and the owner-accepted local type/object redesign from main `2122f2e68f7f22a091ed2f4eadb93273169de8aa`. The outcome is `grace library rename <path> <new-name>` for one clean synchronized nonempty file in its existing parent, using two onboarded Windows copies and a fixed catalog/root. The [new charter](https://github.com/ScottArbeit/Grace/issues/1073#issuecomment-5594043263) supersedes review and validation evidence for the earlier candidate.

## Implementation and limits

The command stores the selected file/name and generated ID in the existing operation row, freezes the namespace-only request and retains the actual receipt. It uses the existing SDK and ordered incoming application, preserving compatible content revisions and saved edits. A definitively rejected unprepared rename becomes terminal and returns before pull. Cancellation checks at submission and filesystem checks retain incomplete work. Completion rechecks repository state inside the SQLite transaction as well as the exact operation row.

The shared payload-free `Common.ItemKind` is new; explicit local adapters leave wire DTOs unchanged. No server actor, HTTP route, SDK, generated remote client, package, solution or deployment change is included. The three Library tables and classified-history pruning policy remain. `operation_json` stores only its envelope and typed work, with SQL indexes derived on every write. Saved-content references point to verified immutable objects completed before the operation commit. Production code does not use the earlier rename experiment's simplified server, capture or pruning models.

The co-delivered [49-case experiment](Libraries.Rename-Experiment.md) retains its original script/result hashes and model limits. Production tests use actual Windows files, the local serializer and Microsoft.Data.Sqlite, real CLI processes, SDK/HTTP, Cosmos/Azurite-backed server acceptance, retained content reads and dual-hash verification. Cancellation uses the same command service with a token canceled either after receipt retention before feed preparation or after real read preparation. Tests do not claim arbitrary process termination or power-loss safety, nor every experiment interruption as a separately injected production boundary.

## Declaration and scope review

The [type plan](Libraries.Type-Plan.md#issue-1073-local-declarations) inventories every stored field and union case. New production declarations are shared `Common.ItemKind`; `LibraryOperation` with typed intent/progress, receipt/rejection, target/echo and object identity types and named transitions; streaming object capture/verification functions; typed `RenameOutcome`; and `RenameOutput` plus its explicit CLI conversion. `PendingOperation` aliases the typed stored source; its former writable flags and source byte array are removed. `captureSavedWith` exposes the existing post-insert interruption boundary to focused production tests.

Self-review covers exact intent, request, receipt and checkpoint authority; genuine server acceptance; saved-object availability and streaming; derived SQL fields on every write; no-file tombstone completion; ordered rename/saved-content application; object and filesystem obstruction behavior; output schema and owned-path propagation. There is one new compile entry for `LibraryOperation.CLI.fs`; there are no new packages, projects, tables, HTTP routes, remote DTO fields or lifecycle owners.

Watch's exact prepared/terminal classification remains. The command adds no automatic rename inference, directory rename, cross-parent move, deletion, reconciliation, retention policy or WDU completion. The Library guide, maintained design/type plan and CLI AGENTS describe the changed persistence and output. README's command examples, CONTRIBUTING and Watch instructions need no new behavior or workflow guidance beyond those maintained references.
