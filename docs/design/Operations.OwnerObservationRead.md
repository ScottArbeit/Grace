# Owner observation read contract

Status: **Plan-ready for one later public tracer; owner-facing visibility is unimplemented.** This is the selected September 7, 2026 contract for [Issue #1066](https://github.com/ScottArbeit/Grace/issues/1066), under [Issue #554](https://github.com/ScottArbeit/Grace/issues/554). The [executable evidence bundle](Operations.OwnerObservationRead-Experiment.json) records the deciding experiments. It does not implement the API described here.

An owner administrator should be able to read one previously captured DirectoryVersion declaration observation, using its operator-supplied ID and recorded scope, without losing quantity or timestamp precision. This gives owners a first useful reading while retaining the distinction between observed declarations, complete storage coverage, elapsed usage and charges.

## Existing source and meaning

[`DirectoryVersionSizeObservation`](../../src/Grace.Types/UsageObservation.Types.fs) contains `ObservationId`, `Scope`, `DeclaredLogicalBytes`, `DistinctContentCount`, `EnumerationStartedAt` and `EnumerationFinishedAt`. `Scope` is the existing [`UsageFactScope`](../../src/Grace.Types/Usage.Types.fs), containing OwnerId, OrganizationId and RepositoryId. The record's validator requires nonempty IDs, nonnegative signed 64-bit quantities and a complete nonreversed enumeration window.

The bytes describe logical bytes declared by surviving DirectoryVersion records encountered during the completed bounded enumeration. Distinct content follows the existing whole-file storage-key and manifest-address rules documented in [Operations](../Operations.md#measurement-boundary-selected-by-issue-1045). A zero reading is a real completed reading. It is not missing data. Do not relabel either quantity as all repository storage, physical storage, elapsed bytes-minutes or a billable total. Do not sum this source with TextContent or Artifact as though their coverage were disjoint.

[`DirectoryVersionSizeObservations.lookup`](../../src/Grace.Operations.Data/DirectoryVersionSizeObservation.fs) selects one immutable SQL row by ObservationId and checks all three scope IDs. Missing returns `Ok None`; a conflicting scope returns `Error` without a stored payload; unavailable SQL throws. The existing [`DirectoryVersionSizeObservation.Read`](../../src/Grace.Server/DirectoryVersionSizeObservation.Server.fs) is SystemAdmin-only and has no live repository check. The new owner path must reuse this lookup, preserve the table and acceptance transaction, and project scope conflict to 404 locally.

## Public read behavior

The selected route is `GET /owner/usage/directory-version-observations/{observationId}` with required `OwnerId`, `OrganizationId` and `RepositoryId` query parameters. Each must parse as a nonempty GUID. There is no request-body contract. The existing `GetRepositoryParameters` is reused as an internal/SDK carrier, not as a promise to accept all of its inherited selectors.

Reject malformed or missing IDs, the empty GUID, and nonempty OwnerName, OrganizationName or RepositoryName selectors with 400. Empty name fields select nothing. No current-owner/repository defaults or name-to-ID resolution occurs. Existing correlation headers/metadata retain their diagnostic role; caller-supplied `Principal` does not replace the authenticated principal or grant permission. Unknown parameters do not introduce new feature inputs.

The success body is the existing `GraceReturnValue<DirectoryVersionSizeObservation>` envelope with the unchanged record in `ReturnValue`. ID fields remain GUID strings. Both quantities are explicit JSON strings representing integers in `[0, 9223372036854775807]`, with no sign, fraction, exponent or leading zero except `"0"`. Both timestamps are exact UTC strings using the existing Instant serialization, retaining all represented fractional digits, including nanoseconds. They describe the original enumeration, not this read's start/end. Envelope metadata such as correlation and server timing is not required to be byte-identical between requests; the observation's values are immutable.

The route-local options clone retains Grace's F# and NodaTime converters and adds `WriteAsString` alongside `AllowReadingFromString`. The unmodified shared F# reader can reconstruct the original int64/Instant fields. The public observation component declares these fields as strings. Its timestamp fields must not reference the shared `Instant` date-time component or introduce generated JavaScript `Date` coercion. Descriptions/examples must state the actual existing Instant range and precision; the experiment's narrow four-digit-year regex is only a fixture and is not a selected runtime validator or complete production range definition. Global JSON options and unrelated schema components stay unchanged.

The selected F# entry point is a method on existing `Grace.SDK.Owner` taking an ObservationId `Guid` and `GetRepositoryParameters`, returning the existing Grace result for the existing record. It constructs the encoded query route and uses `Common.getServer`; it must not call the existing owner-profile POST endpoint. Invalid explicit selectors must fail without filling values from current configuration.

The selected CLI entry is `grace owner get-directory-version-observation`, with required `--observation-id`, `--owner-id`, `--organization-id` and `--repository-id`. It calls that SDK method, writes the complete observation with decimal-string quantities and exact timestamp strings in machine-readable output, and retains the existing CLI exit/error conventions and envelope. Human-readable output must retain the complete values and source-specific labels too. Passing a typed record through the ordinary shared numeric serializer would lose the selected public representation. The command can serialize its existing record with local options into an existing `JsonElement` before supplying it to the common renderer, preserving strings through JSON output and selection without another DTO or global option change. Its explicit schema/examples registration must describe this representation. This is a future command contract, not an available command.

TypeScript Node callers use the supported `GraceClient.request` facade with GET, the exact path and string query GUIDs. The facade preserves the parsed JSON strings; consumers must not convert the observation quantities to `number` or timestamps to `Date` when preserving the record. `BigInt` can be used locally for arithmetic, with conversion back to decimal strings for JSON. A usage example and test belong on the facade surface. No newly advertised endpoint-specific TypeScript API or raw-model package export is required. Browser TypeScript, Python and Rust facade expansion are deferred; their existing raw-generator matrix checks remain part of repository contract freshness.

## Permission and effect sequence

The primary invariant is: disclose only the unchanged observation whose ID and complete scope match the request, after the most recent required permission evaluation allows OwnerAdmin on that owner. Stored SQL facts decide the observation values and historical binding. Current AccessControl assignments, evaluated with the authenticated request principals/claims and existing RoleCatalog, decide permission. Request IDs alone never grant access.

1. Authenticate through the existing middleware before resolving inputs. An unauthenticated request performs no permission evaluation, SQL lookup, name resolution or live repository lookup, even if its IDs are malformed.
2. Parse the explicit ID tuple and resolve `OwnerAdmin` on the requested OwnerId. Do not attach ordinary body-parameter metadata that would cause `ValidateIdsMiddleware` to resolve current entities before the route's authentication/validation. The query resolver can use `requiresPermissionResolved` and ordinary functions.
3. Run the initial existing permission evaluation. Denial or evaluator failure ends the request with 403 and no SQL lookup.
4. Await exactly one existing SQL lookup for the ObservationId and complete requested scope. The lookup reads only; it never captures a reading or updates a row.
5. Re-read permissions through the same existing evaluator after the lookup, for the same owner and authenticated principals/claims. Do this for missing/conflicting results too, before choosing the response. Do not reuse the first decision or its assignment snapshot.
6. If still allowed, map missing/scope conflict to 404 without stored values. Otherwise return the exact matching observation using the local serializer. Check cancellation before publication. Any failure before publication returns no observation.

| Situation | Result and effects |
| --- | --- |
| Unauthenticated | Existing 401 authentication response; no ID resolution, permission evaluation or lookup. |
| Invalid explicit input after authentication | Grace error, 400; no observation lookup. |
| Initial permission denial or evaluator failure | Existing permission denial, 403; no SQL lookup. |
| Revocation detected by the second check, or second evaluator failure | 403; no observation is published, including when the SQL lookup had found a row. |
| Missing ObservationId or any stored identity/scope mismatch after successful permission checks | Grace error, 404; no stored IDs, quantities or timestamps. No existence-revealing 409 on this route. |
| Unavailable/failed/cancelled read or failure before publication | Grace error, 503 while the connection can still carry a response; no observation. Client disconnect may prevent delivery of the status itself. |
| Matching stored observation and both checks allow | 200 with the exact existing observation in the Grace success envelope. |
| Permission revoked after the final evaluation | The already-authorized response may still be delivered. No atomic revocation/delivery guarantee. |

Permission failure is the evaluator's existing denied outcome, not a storage-unavailable 503. The future route should reuse the current bounded read/cancellation pattern and must not expose an observation in an error or diagnostic log. The modeled experiment does not implement production exception mapping or HTTP serialization.

There are no durable effects, partial capture states, cleanup jobs or recovery records in this read. A failed, cancelled or disconnected request may be retried with the same tuple; the new request repeats authentication and permission checks and reads the retained row. A lost success response creates no uncertain write. A later permission result may differ even though the stored values do not. The operation offers no automatic retry schedule or new availability guarantee.

The second evaluation reloads assignments through existing callbacks. It does not refresh authentication tokens, group membership claims or external identity state, and the evaluator has no atomic snapshot across the scoped assignment reads or HTTP delivery. The contract accepts those existing request-identity and evaluation limits. It adds no lock, cache invalidation protocol, subscription or permission-version model.
