## Outcome and delivery

An authorized participant edits ordinary nonempty files in a repository-owned Library. Grace transfers accepted bytes and changes between participating working copies without creating Saves, References, DirectoryVersions or WorkItem Attachments. Local zero-byte files are excluded before pending input or upload preparation; they remain present and protected from incoming overwrite or deletion. Previously captured nonempty input remains durable after a later zero-length save.

One configured repository-relative root is one Library. A repository owns a sorted catalog of at most 128 non-overlapping roots. Adding a root requires an empty outgoing version-control namespace; removing it requires an empty Library namespace. A catalog change changes path ownership, never imports or moves files.

The delivered Windows client supports two authorized copies and one unchanged Library root. A publishes nonempty files and nested directories; a fresh B joins with an empty local Library root, installs exact selected baseline revisions, catches up with changes accepted after selection, and restarts without duplicate publication or completed-file rewrites. The accepted additive catalog-adoption slice below extends already onboarded copies to exactly two roots; it is not implemented. Existing-file reconciliation, general catalog adoption and automatic rebaseline remain deferred.

The explicit command lets a user rename one synchronized nonempty file within its directory while both Windows copies retain the same item and content history. The accepted command and failure behavior appear below. Automatic recognition of an Explorer rename remains deferred.

PR #1076 delivered local durable pause/resume for an already onboarded Windows copy, including the accepted GUID-backed epoch contract. The next accepted slice permits explicit adoption of one added root while preserving pause and completed progress. Broader offline behavior, namespace gestures, other ownership transitions, and Linux/macOS conformance remain later epic work. Public history browsing, restore, diff, search, AI assistance, Cache, placeholders and on-demand hydration remain deferred. No new WDU caller, database, general locking service, migration layer or alternative platform state machine is included.

## Accepted choices

All replacement choices in the report are accepted, including compact item/slot history, immutable-version signed reads, notification progress and the three-table client. They are subject to the listed experiments, not another approval of the same choices.

- One `RepositoryLibraryActor` orders Library changes for each repository.
- Every Library metadata write and clear goes through the registered Orleans provider from that actor.
- Cosmos SQL performs aggregate and cross-record reads when Cosmos is configured. No actor directory substitutes for queries.
- Stable item identity and parent/name relationships survive renames and moves.
- Content revision records edit order; deterministic content identity permits equal bytes to share storage.
- Every baseline build may pause Library changes until its complete manifest is published.
- Keep accepted change records and referenced historical bytes permanently. History indexes can be rebuilt.
- Keep one send-progress cursor and at most one failed envelope. Notifications remain advisory.
- Local persistence uses repository state, materialized items and durable operations in the existing SQLite database.
- Keep established upload, content-counter and manifest-workflow owners. No per-record Library actors remain.
- Use the [type plan](design/Libraries.Type-Plan.md) to apply the 173 reviewed dispositions. The counts are an inventory, not a quota.

## Authorization, public behavior and bounds

Repository administrators manage the catalog. Library readers may read permitted catalog, items, slots, pages, receipts, bytes and wake hints; writers may also prepare bytes and submit changes. Recheck repository identity and permissions at disclosure, acceptance and content transfer. Preserve missing/cross-repository no-oracle responses and the existing content integrity checks.

Keep the fifteen existing `/libraries` routes and their SDK operations. Change their Library DTOs together as described below, including typed upload preparation, immutable content reads and revision preconditions. Update HTTP validation, OpenAPI, generated TypeScript/Python/Rust clients and examples in the same remote delivery. Public cursors and page/read tokens stay opaque, repository-bound, purpose-bound and signed; page/read tokens expire. Token keys remain deployment configuration, stable across server instances.

Keep stable operation IDs. Normalize and hash each complete request once. Identical retries return the same recorded result; different input under the same operation ID is rejected. Receipt recovery precedes upload-expiry checks.

Library roots use relative path segments, reject absolute/traversal/reserved metadata paths, and compare normalized names using the accepted NFC and ordinal-ignore-case rules. Root matching respects segment boundaries: `shared` owns `shared/file.txt`, not `shared-old`. Full item paths are derived from parent links. The path limit is 1,024 UTF-8 bytes. The repository limit is 100,000 retained item heads and 100,000 retained slots, counting tombstones and vacancies.

Keep content-free status and `LibraryContentAvailable.v1` wake behavior. A wake prompts a pull; only accepted changes determine order. There is no promise of immediate notification after an idle silo restart without a request or existing activation trigger.

Keep `grace library` catalog commands and the `grace library sync enable|run|status` commands delivered in Issue #1039. Preserve the normal human and `cli-json-v1` output conventions. Issue #1071 extends enable/run to populated-Library onboarding. The accepted pause/resume additions below do not disable participation, adopt a catalog or rebaseline an existing tree.

Catalog add/remove commands accept optional `--expected-version` and `--operation-id`. An omitted version causes one scoped catalog read; an omitted operation ID creates one invocation-local ID. Explicit values are retained. Lookup failure prevents mutation, and a stale result remains visible without retry. Exact scripted retries retain both explicit values and all other request details. This changes only the CLI adapter; the server's exact-version and operation-replay contracts remain unchanged. The five support modules live in `src/Grace.CLI/Library/`, with the command entry point at `src/Grace.CLI/Command/Library.CLI.fs`.

## Explicit file rename: delivered

Delivery: **complete in PR #1074**, Product V1, for `grace library rename <path> <new-name>` in the configured Windows working copy. Scott accepted the [checkpoint recommendations](https://github.com/ScottArbeit/Grace/issues/1037#issuecomment-5591691687); the [decision record](https://github.com/ScottArbeit/Grace/issues/1037#issuecomment-5591944045) and [experiment](design/Libraries.Rename-Experiment.md) established the unchanged command and rejection/resume contract. Issue #1073 delivered production acceptance and the accepted local type/object redesign.

Support two authorized Windows 11 copies with completed onboarding, one unchanged catalog/root, one clean materialized nonempty file, and an absent destination within its existing parent. Derive item, parent and namespace version from materialized state using the existing path/name normalization rules. Reject a dirty or absent source, directories, reparse paths, excluded zero-byte files, cross-parent paths, normalized-equivalent names including case-only changes, and pending work that prevents a clean start. General reconciliation, automatic filesystem rename inference, deletion, directory rename, move, catalog adoption and other platforms remain deferred.

One frozen intent addresses one stable item. The existing server decides namespace changes. The local command supplies the item's namespace precondition, never a content precondition, upload or client slot expectation. A concurrent content edit is compatible; a competing namespace change, deleted item or occupied destination receives the existing server outcome. Do not retarget a rejected request or allocate another identity to make it succeed.

1. Acquire existing root exclusion. Recheck participation, current catalog/progress, exact materialized item/parent, clean nonempty source and absent destination. Persist the selected intent and generated operation identity before submission, without changing local filenames.
1. Freeze the complete existing submit request in the operation row. A repeated pending invocation with the same source/name resumes that row; a different name cannot replace it. Ambiguous responses and cancellation retain the same request and identity for receipt recovery/retry.
1. Persist the genuine server receipt. Acceptance alone does not update materialized state or applied progress. Pull changes in order from the actual applied predecessor, including compatible edits accepted before the rename. Never apply a newer accepted receipt directly across an unapplied predecessor.
1. Use the existing incoming file-rename preparation and application sequence. Preserve the original materialized base and prepared destination evidence, stage and verify the accepted retained bytes, revalidate, publish the destination, then revalidate and remove the old source. Reuse an exact prepared destination after interruption. A changed source or destination requires the existing exact accepted saved-byte evidence before destructive effects. Zero-byte files and other obstructions remain present and block progress.
1. After verifying filesystem completion, commit item, terminal operation and applied cursor together with exact-state/operation update checks inside SQLite. A failed check rolls back the transaction. Root exclusion, point-in-time filesystem checks and exact prepared/terminal Watch classification retain their current concurrency guarantee.

A definitive rejected rename receipt retires only that unprepared rename intent: retain the receipt/reason in its operation row, mark it terminal with no publication echo, and leave materialized items, applied progress and the command's filenames unchanged. The command reports the rejection; later synchronization can apply unrelated and competing accepted changes. Existing bounded classified-operation pruning already accommodates an accepted-change-free terminal row. No retention policy changes. Do not apply this retirement to a rejected saved-content operation: its bytes/request remain pending under the existing contract.

Report local success only after accepted application and atomic local completion. If the server accepted but local application is obstructed, report acceptance plus incomplete local application and retain resumable work. A lost response is not rejection. A blocked or canceled command must not claim completion. Human and `cli-json-v1` results must distinguish these outcomes using the existing output conventions; users are not required to supply internal operation identity or namespace versions.

The experiment demonstrates the finite sequence with real Windows files, an exclusive file lease and native SQLite. Server decisions, content transfer and Watch classification are models. Production acceptance must use the real command, SDK/HTTP endpoints, retained-read verification, local serializer/SQLite adapter and Watch capture seams. The evidence does not establish process-kill/power-loss guarantees, other platforms or broader namespace gestures.

## Pause and resume: accepted next slice

Readiness: **Plan-ready**, Product V1, for one bounded Windows mainline slice. The [accepted decision record](https://github.com/ScottArbeit/Grace/issues/1037#issuecomment-5597448981) settles the following behavior. The [experiment report](design/Libraries.Pause-Experiment.md) records 56/56 cases against source `66aea34838a65a9e4b220463f0d8366836ee328d`, distinguishes modeled boundaries from production execution, and names remaining delivery tests. Issue #1075 implements this behavior; the [validation mapping](design/Libraries.Pause-Validation.md) records production tests and remaining review gates.

Users can pause one onboarded copy while another continues, then resume without abandoning the copy or losing exact selected work. Support two authorized Windows 11 copies of one repository, completed onboarding, one unchanged catalog/root, existing nonempty-file captures and explicit rename, and catch-up through the existing feed. Include frozen/uncertain submissions, rejected saved work, partly applied accepted work and retained terminal echo records. Incomplete onboarding, disabling/removing participation, per-Library selection, filesystem rename/delete inference, automatic rebaseline/reconciliation, changed-root adoption and other platforms are excluded. Existing completed baseline records may remain in terminal history; they are not incomplete onboarding.

### Commands and observable behavior

| Command or event | Required behavior |
| --- | --- |
| `grace library sync pause` | Wait with cancellation for the existing root lease. Reread participation, require completed onboarding, then persist pause locally without draining the queue or contacting the server. Return success only after the pause commit. An already paused copy is an idempotent success. |
| `grace library sync resume` | Under the same lease, require existing completed participation and commit active participation before attempting a finite synchronization run. Repeating resume is safe. It does not enable a never-participating copy or restart bootstrap. |
| `run`, `enable`, or `rename` while paused | Report pause and direct the user to `sync resume`; do not clear pause, capture, submit, apply or retire pending work. Return nonzero for the blocked action. |
| Watch, capture, echo classification and pruning | Skip Library work while paused. Reread pause after obtaining the root lease; a cached `Enabled` result is insufficient. A wake may be dropped or coalesced. Resume pulls even without a wake. |
| Status and process restart | Retain `Enabled=true` for an existing participant; add `Paused` as an independent Boolean. Preserve the existing progress `State`, catalog/cursor and pending count. Human output shows both pause and progress. No row means disabled and not paused. |
| Resume encounters an error | Leave participation active; preserve the existing visible blocked result and exact pending work. Watch or `run` may retry through unchanged checks. A changed catalog, epoch/rebaseline requirement, missing object, zero-byte obstruction or rejected saved content never authorizes reset, substitution or discard. |

Pause does not immediately interrupt the active lease holder. That holder may finish or stop before pause acquires the lease; cancellation while waiting changes nothing. Pause does not undo server acceptance or roll back filenames. An interrupted commit is resolved by reading the row: before/rolled-back commit retains the old setting, after commit retains the new setting even if the response was lost. No separate command receipt or pending pause operation is needed.

Pause stops new Library capture as well as transfer. Already captured immutable objects and exact operation payloads remain retained. On resume, capture the latest supported saved disk content against the last materialized edit base before incoming application can replace it. Do not promise every intermediate save made and replaced while paused. Preserve the existing revision-based conflict rules and protections for saves at either path of a prepared rename. Empty files remain excluded and protected.

### Persistence, effect order and competing callers

The one new durable value is `RepositoryState.Paused`, stored as a constrained Boolean column on `library_repository_state`, independently from `lifecycle_state`. Keep the three existing Library table responsibilities and all accepted operation variants and object references. Update current schema/read/write/equality paths together; no migration or compatibility layer for hypothetical old production data is required.

The local repository row under the shared root lease decides whether Library work may run. Every admitted command, timer, capture/classification and pruning path rechecks it under that lease. Status is advisory and does not grant permission to mutate. Retain the catalog, materialized ancestry, exact operation/checkpoint and point-in-time filesystem checks immediately before their existing effects and completion. Pause does not change catalog ownership or permit Library files to enter Save, Branch or WDU content.

For resume, commit `Paused=false`, then use the existing finite run. If the lease is released between the setting change and that run, the run must acquire it and reread pause. A newer pause wins; the earlier resume must not clear it again or claim current completion. Production transaction comparisons include the new pause value, while ordinary progress updates preserve it. Do not reacquire a non-reentrant root lease from a helper that already holds it.

Unchanged saved-content and rename algorithms retain their prior accepted experiment and hosted evidence. The new experiment establishes the pause setting, serialization/retention, real lease and transaction boundaries. Its remote acceptance, capture orchestration and Watch entry calls are models. Production delivery must use real CLI/HTTP A/B synchronization and a running Watch process racing pause/resume, including actual capture/upload, pending response loss, partial rename, later local save with a compatible remote edit, restart and catalog/rebaseline stops.

This slice does not promise a fully offline Watch process. Watch still reads the catalog outside Library synchronization for namespace classification. Keep those checks and the existing Watch/SignalR lifecycle; do not turn this work into whole-Watch network recovery.

### Delivery and stop conditions

Use one Tier 2 mainline slice from freshly pinned `origin/main`, one controller and one implementation owner, with its own issue readiness and run charter. Co-deliver this documentation and experiment evidence; the readiness branch is not required ancestry or an enabling production PR. Require focused production tests, status/schema/help propagation, independent R1, one consolidated accepted repair pass and bounded R2 if needed, Shape Review and current-head GitHub Validate. No routine duplicate local Fast/Full gate.

Stop for another owner, table/database, independent recovery lifecycle, changed retention/conflict/zero-byte/rejection behavior, broader reconciliation, another gesture/platform, whole-Watch offline guarantees, changed delivery mode or a third enabling PR. If an admitted pending state cannot be handled, return that exact decision to Scott rather than excluding it silently. The accepted pause and resume decisions do not require another confirmation.

## Identify each item by its parent and name

`LibraryNamespaceDto = { Parent; Name; NamespaceVersion }`. A root parent names a configured Library path; an item parent names a stable directory item. A slot is keyed by `(repository, parent identity, normalized sibling name)`. Full paths are derived views. Remove `NormalizedPath` from the shared namespace/slot contracts and update the client to resolve the parent graph; do not store a path that silently becomes stale after an ancestor moves.

Example: directory D is `assets/design`; file F has parent D and name `logo.svg`. Moving D to `shared/design` changes D's parent edge and its two affected slots. F still has parent D. Its path becomes `shared/design/logo.svg` without rewriting F or manufacturing a content revision. A client with the current item graph derives the same result. Historical paths use the graph at the historical cursor.

Before moving a directory, walk the destination’s parent chain and reject a move into the directory itself or one of its descendants. Check that the current catalog allows both locations. To enforce the 1,024-byte path limit, read the bounded current namespace while the actor holds its turn and calculate the new paths of affected descendants. This requires a query and an in-memory traversal, but no writes to descendant records. Use SQL to check for live children before deleting a directory. Check that a Library is empty inside the actor before removing its root; an earlier HTTP query can be stale.

For a stale-content conflict, compute a deterministic candidate sibling name, read that exact slot, and try deterministic numbered alternatives while occupied. Select and persist the winning name and new item ID in Pending before any projection writes. A user-created filename may collide with the first candidate. Retries reuse the selected result; they never reallocate a different sibling after acceptance.

Historical review evidence: [conflict allocation](https://github.com/ScottArbeit/Grace/blob/6399d4db015085a1185eb7e367a8d24ece6ddbaa/src/Grace.Server/Library.Coordinator.Server.fs#L791) had no occupancy read for its generated name; [rename/move](https://github.com/ScottArbeit/Grace/blob/6399d4db015085a1185eb7e367a8d24ece6ddbaa/src/Grace.Server/Library.Coordinator.Server.fs#L830) changed only the selected item's stored path; [slot projection](https://github.com/ScottArbeit/Grace/blob/6399d4db015085a1185eb7e367a8d24ece6ddbaa/src/Grace.Server/Library.Coordinator.Server.fs#L284) hashed that path. The accepted parent/name model replaces these inherited behaviors.

## Keep useful public distinctions; remove nested copies

| Contract | Recommended shape | Removed duplication |
| --- | --- | --- |
| Item | `{ ItemId; ItemKind; LastChangeCursor; Namespace?; Content?; Tombstone? }`, plus the accepted separate ContentRevision. | Derive live/tombstoned state. Catalog version belongs to the catalog/change, not every current item. Validate live file, live directory and tombstone combinations centrally. |
| Namespace slot | `{ Parent; Name; SlotVersion; OccupantItemId? }`. | Derive occupied/vacant. Slot version stays here instead of being copied into the item's namespace. |
| Tombstone | `{ DeletedAt; DeletedBy; DeleteCursor; LastNamespace; LastContentVersionId? }`. | Item ID/kind already belong to the containing item. Preserve the last parent edge, not only its version. |
| Accepted change | `{ OperationId; ChangeKind; AcceptedAt; AcceptedBy; LibraryCatalogVersion; Item; Conflict? }`. | One resulting item replaces parallel item ID/kind/namespace/content/tombstone fields. Its LastChangeCursor is the public change cursor. |
| Conflict provenance | `{ OriginalItemId; BaseContentVersionId?; BaseContentRevision? }`. | Source operation, resulting conflict item/path/content and acceptance instant are already in the change. Keep the causal relationship, not another snapshot of the result. |
| Operation receipt | Operation/hash/outcome plus one accepted Change or a rejection's reason/catalog/rebaseline evidence. | Remove parallel Item, Cursor, Conflict and accepted metadata copies. The accepted storage record references its accepted change. |
| Prepare content | `{ UploadSessionId; Blake3Hash; Sha256Hash; Size; AuthorizedScope; StoragePoolId; ExpiresAt }`. | No second prepared-content identity, always-true UploadRequired or JSON string containing another anonymous request contract. SDK methods already name the upload routes. |
| Read content | `{ DownloadPath; Content; ExpiresAt }`, named `LibraryContentReadDto`. | No duplicated GrantId token or consumed-grant fiction. The token binds a retained immutable version. |

**Check that the requested bytes belong to an accepted revision.** Add `ContentRevision` to the read request. Decode its repository-bound cursor, read the accepted-change record, and check the item and content IDs. This still works after a later edit changes the item. A content-location record left by an unaccepted upload is not enough to issue a read URL. Once issued, the URL names that accepted content until expiry.

The small parent, content, tombstone, precondition and result DTOs remain part of the design. Keep public parameter classes and SDK/CLI command adapters where Grace uses them consistently. Do not turn them into a single optional-field request or add a hand-written enum beside every OpenAPI enum. Since Library is unused, change the Library contract coherently instead of adding compatibility aliases or version-translation layers.

Keep six storage purposes and the accepted full partition keys. The registered Orleans provider owns outer document ID, grain type and partition fields. Each inner state keeps its schema version and semantic fields; do not repeat outer routing merely because the old direct Cosmos document did. **Why keep both journal and current records?** The journal answers what was accepted and supports exact retry/history. Current records answer point/aggregate queries without replaying a repository's lifetime. Their duplication buys a necessary access path. Pending buys crash recovery; receipts buy operation-ID lookup; history cursor lists buy targeted access; immutable baselines buy stable paged transfer. The removed indexes and repeated payloads provide weaker benefits at substantially more cost.

**History policy status:** the accepted Product V1 design keeps compact indexes, both tail fields and `HistoryThrough`. The permanent journal and historical content remain independently durable.

## One acceptance protocol, with explicit crash behavior

1. **Enter the serialized repository turn and repair.** Revalidate the repository identity and authorization. Finish any earlier Pending. Look up this operation ID and compare its normalized request hash before resolving temporary upload state. An exact retry returns the recorded result even after preparation expiry; different input under the same ID fails.
1. **Check the current state before choosing a result.** For a new command, check the catalog, parent chain, namespace and content versions, destination vacancy and capacity. File commands also check the completed UploadSession’s operation, principal, hashes, size and expiry, then create or reuse the stored content mapping. An upload does not itself change the namespace. If the mapping is written but reservation fails, it remains unused under the current no-cleanup policy.
1. **Reserve one complete decision.** CAS control with Pending, including the chosen item ID, result, slot generations, cursor, timestamps, correlation and admission deltas. Before that write, a failure accepts nothing. After it, recovery completes that decision rather than reconsidering its outcome.
1. **Write the accepted-change record.** Create it at the reserved key. If the write’s result is uncertain, reread and compare it; stop if the stored record differs. A changed in-memory object does not establish that the storage write succeeded.
1. **Retain accepted content before publication.** Use the existing counter's tracked add and manifest workflow, with stable operation identity. The original zero-transition revision remains recoverable across later ordinary references and absent Redis. Wait for the existing workflow's completion. Each accepted content-bearing operation contributes one permanent historical reference; do not optimize this to one per byte identity in this redesign.
1. **Write deterministic synchronous projections and the operation result.** Upsert the resulting item and at most the old/new slot by cursor; write the accepted receipt reference. Same cursor requires the same semantic value, later cursor never regresses. Replaying a finished receipt must skip re-adding the contribution. Acknowledge the tracked add only after workflow and receipt durability.
1. **Complete control.** Advance CommittedCursor and admission counts by the stored deltas and clear Pending in one CAS. Only then may an accepted result be returned as terminal or exposed by committed delta/current reads. A crash before completion replays the same decision; receipt presence alone is insufficient.
1. **Update history and send notifications in bounded batches.** Read accepted changes to fill history indexes and construct notification messages. Send each message first; save its envelope only after the SDK reports a terminal failure. Acceptance can continue while history is behind or Service Bus is unavailable. Activation and the existing repair, status and operation paths resume this work. An Orleans timer may continue a drain while the actor is active; no new global scheduler is added.

**Catalog changes use the same Pending slot.** The actor checks the current expected catalog version and Library emptiness itself. For an accepted change, record the chosen catalog delta in Pending, derive and persist the exact unified operation result, then CAS the new catalog and clear Pending. Rejection is an immutable operation result with no catalog mutation. Request replay repairs before reporting success. Move catalog decision-making out of [the HTTP handler](https://github.com/ScottArbeit/Grace/blob/6399d4db015085a1185eb7e367a8d24ece6ddbaa/src/Grace.Server/Library.Server.fs#L390); remove the catalog-specific provisional/committed bridge. For version-control emptiness, supply immutable Reference/DirectoryVersion evidence through a narrow function and respect the already accepted IsInLibrary race; do not create a cross-domain reservation or call RepositoryActor back from its creation workflow.

| Failure point | Durable evidence | Required recovery |
| --- | --- | --- |
| Reservation response lost | Control either contains the complete Pending or does not. | Reload control before choosing again. Same operation cannot acquire a different ID/cursor/result. |
| Accepted-change or projection write throws | Fresh provider state + ETag, not a shared mutable buffer. | Discard the candidate buffer, reread and compare. Continue only from confirmed durable state; deactivate on unexplained conflict. |
| Counter committed, workflow not started | Existing PendingTrackedAdd retains operation and zero-transition revision. | Resume that exact workflow, without an extra reference increment. |
| Receipt exists, control still Pending | Saved decision and receipt reference agree; tracked completion may already have occurred. | Skip re-add, finish acknowledgement idempotently, complete control, then return success. |
| Commit done, first notification never sent | CommittedCursor > NotifyThrough; accepted-change metadata retained. | Next activation/recovery resumes from NotifyThrough + 1. No scan over every possible historical fallback actor. |
| Send succeeds, progress write fails | NotifyThrough has not advanced; failed envelope may or may not exist. | Resend with stable MessageId. Duplicate transport delivery is allowed. Consumers use accepted cursor/order. |
| Fallback clear fails after progress advances | NotifyThrough records that the send succeeded; the saved failed envelope belongs to an earlier cursor. | Clear the obsolete fallback before attempting the next one; never mistake it for the current unsent change. |

**NotifyThrough is an intentional addition.** It replaces unbounded per-cursor fallback probing with one recoverable position and one failure slot. It adds a small successful-send progress write to control, but no successful-send envelope/outbox record. It is not interchangeable with HistoryThrough: a Service Bus outage must not block history indexing. This accepted change replaces the old implementation; Orleans does not require it. An idle repository still needs an existing activation/request trigger after a silo restart; this design does not claim guaranteed wall-clock notification delivery without a durable wake mechanism.

## Baselines: use the approved pause to remove the race

The feed epoch identifies one repository generation. `LibraryCursorEpoch` is a distinct GUID-backed value compared only for equality; it has no ordering or timestamp meaning. HTTP, events, status and SQLite encode it as a hyphenated GUID in D format and reject malformed epoch text at read boundaries. Applied cursors remain opaque signed tokens. The server's control and baseline manifest retain their existing GUID epoch fields.

1. In one non-reentrant RepositoryLibraryActor call, finish Pending and capture committed boundary B, epoch and catalog. Reuse a complete baseline at the deterministic key if present.
1. Establish current-partition read visibility. The SQL client and providers share a singleton CosmosClient per silo. On a fresh activation, validate the control ETag; for B > 0, point-read the last accepted change's item using that query client until its LastCursor equals B. No later Library write can occur during this turn. Failure to establish visibility aborts the build; it does not publish a partial snapshot.
1. Enumerate every current-item record, including tombstones, with parameterized SQL and continuation paging in full partition `[repo,item]`. Verify the admitted record count and that no item cursor exceeds B. Resolve live parent edges and reject a malformed live graph. Retained tombstones may refer to formerly configured roots; do not require historical edges to belong to the current catalog. Current state size, not lifetime history, bounds this work.
1. Sort deterministically, serialize through the real configured codec, pack byte-bounded shards and persist them through Orleans. Hash the exact defined shard bytes with BLAKE3. Derive shard IDs; a retry must not depend on a failed build's volatile timestamps.
1. Write the complete manifest last. The manifest's existence is the publication point. No control baseline pointer, separate snapshot actor, double collect, concurrent-tail overlay or durable build status is needed.
1. Release the turn. Serve requested pages by manifest shard counts, loading only intersecting shards. Validate token repository/purpose/baseline/offset/expiry. Old published baselines remain valid for their token lifetime; they are immutable even while new changes resume.

Build cancellation before publication leaves only unpublished shards. Exact keys permit a retry at the same boundary; if the repository has advanced, build the new boundary and leave old residue under the accepted retention policy. Measure elapsed pause, peak memory, RU, request timeout/retry behavior and serialized headroom at 100,000 items. The owner approved a pause, not an unmeasured latency promise. No temporary concurrency framework is warranted before those measurements.

## Cosmos SQL reads are part of the design

Keep the full partition key on each query. The approved provider stores the outer fields as `PartitionKey`, `PartitionKey2`, `PartitionKey3` and `State`; check their casing with the configured JSON serializer. Set the complete SDK request partition key as well as the SQL conditions. Index the fields these queries use.

```text
-- Current namespace, with continuation paging; PK [repo, "item"]
SELECT c.State FROM c
WHERE c.PartitionKey = @repo AND c.PartitionKey2 = "item"
ORDER BY c.id

-- Directory emptiness; PK [repo, "item"]
SELECT TOP 1 VALUE c.id FROM c
WHERE c.PartitionKey = @repo AND c.PartitionKey2 = "item"
  AND IS_NULL(c.State.Item.Tombstone)
  AND c.State.Item.Namespace.Parent.Kind = "item"
  AND c.State.Item.Namespace.Parent.ItemId = @directoryId

-- One ordered segment of accepted changes; PK [repo, segment]
SELECT c.State FROM c
WHERE c.PartitionKey = @repo AND c.PartitionKey2 = @segment
  AND c.State.Cursor > @after AND c.State.Cursor <= @committed
ORDER BY c.State.Cursor
```

The storage experiment observed that the configured F# option converter writes `None` as JSON `null`, including under `WhenWritingDefault`. Use `IS_NULL(...)` for the live-item test. The `NOT IS_DEFINED(...)` control query returned zero for these records. Test the exact nested production paths when the replacement shapes are implemented. Read only the change segments needed for a page. Use point reads for operation, content and baseline records, and follow known segment links for history. One fixed failed-message key avoids a cross-partition scan. The two counts in control enforce capacity; count queries can check those values during validation.

Separate Cosmos clients do not automatically see each other’s recent writes. Sharing a client within a silo helps, but a newly started silo still needs the explicit visibility check. The provider exposes its ETag operations in the approved [CosmosGrainStorage source](https://github.com/ScottArbeit/orleans/blob/12c6f7ea413eede43c1f1a589b51430fcf9ae7ed/src/Azure/Orleans.Persistence.Cosmos/CosmosGrainStorage.cs). See [Microsoft's session-token guidance](https://learn.microsoft.com/en-us/azure/cosmos-db/how-to-manage-consistency#utilize-session-tokens). Test these reads with independent clients and the actual provider JSON before implementation.

```text
HTTP / SDK / CLI

      → LibraryDecision functions: validate and choose
      → LibraryRecords functions: typed registered Orleans provider operations
      → LibraryQueries functions: explicit Cosmos SQL reads
      → LibraryTransfer functions: existing upload / counter / workflow actors
      → LibraryTokens functions: signed cursor, page and read tokens

Existing shared owners retained:
  RepositoryActor → initializes the Library catalog (no callback cycle)
  UploadSessionActor → temporary transfer and cleanup
  RepositoryContentCounterActor → reference count + tracked handoff
  ManifestContributionWorkflowActor → existing range activation
  ContentBlock/range/storage owners → existing immutable bytes
```

Use `RepositoryLibrary.Actor.fs` for the actor and small actor-facing helpers. Move the decision/record/query implementation out of Server services into F# modules in the Actors project, in explicit compile order before the actor. Server keeps HTTP adaptation and composition. A module file is not another actor. Remove `LibraryRecord.Actor.fs` after its 13 classes are gone; do not hide a generic union/object grain there. The existing one-domain-per-actor-file convention remains clear.

`IRepositoryLibraryActor`, existing upload/counter/workflow grain interfaces, `IGrainStorage` and `IDocumentIdProvider` are framework or distributed boundaries. Keep them. `ILibraryStore`, `ILibraryTransferStore`, `IGraceEventSender` and `ILibraryManifestContributionActivator` are application abstractions introduced by composition/testing choices. Replace them with functions that own a small behavior. Passing a send or authorization function where needed is enough; do not replace four interfaces with a giant “dependencies” record containing all their members.

The existing [IGrainStorage API](https://github.com/dotnet/orleans/blob/v10.2.2/src/Orleans.Core/Providers/IGrainStorage.cs) accepts typed state, state name and GrainId. Private functions can address deterministic record keys without activating a grain for each key. Those functions use the registered provider after Orleans initializes it. Create a fresh `GrainState<T>` for each attempt. Check the repository and key, use the last-read ETag, and reread storage after an uncertain write. The [standard state bridge](https://github.com/dotnet/orleans/blob/v10.2.2/src/Orleans.Runtime/Storage/StateStorageBridge.cs) additionally supplies runtime checks, tracing and migration behavior. Direct provider calls need logging and metrics. Keep these records out of cached activation and migration state. The public API supports this approach, but a Grace prototype still needs to exercise writes, failures and restarts.

## Alice editing while Bob's changes arrive

**Server acceptance order decides when an edit enters Library history. SignalR arrival time and the time someone opened an editor do not.** A local edit keeps the base against which its bytes diverged. Receiving a newer server head must not silently rewrite that base.

| Step | Server | Alice's disk and local facts |
| --- | --- | --- |
| Initial | r1 contains X. | Disk X; last materialized base r1/X. |
| Alice saves her edit | Still r1. | Disk Z differs from X. Pending local operation records r1 as its content base and freezes the exact candidate bytes before upload. |
| Bob submits Y, then X | Accepts r2/Y, r3/X. | Notification wakes catch-up. Received changes can be recorded as pending remote work. Preserve Z and r1; do not claim that r2/r3 have been applied to disk. |
| Alice submits Z | Submission is considered after r3. Byte identity is X in both r1 and r3, but their edit history differs. | With revision comparison, her request is stale and Z becomes a deterministic sibling conflict item. With byte-state comparison, Z replaces current X. Revision comparison is the owner-accepted choice. |
| Finish locally | Accepted result is durable and retryable. | Preserve/publish the accepted sibling when needed, install the server’s current version at the original path only when safe, and advance the applied cursor after the relevant filesystem/SQLite completion. Later edits to Z are a new pending operation, not an amendment to an in-flight request hash. |

**Owner-accepted choice:** compare a content revision in addition to content identity. Add `ContentRevision: LibraryCursor` to the item projection and `ExpectedContentRevision` to the content precondition; update it only for content acceptance, never a compatible rename. Keep `ContentVersionId` deterministic from bytes for storage reuse. Scott accepted this behavior after the editing explanation. This changes the Library concurrency contract while preserving deterministic byte identity and storage reuse.

A watcher cannot see unsaved editor memory. If disk X is unchanged while Alice has an unsaved buffer, Grace has no filesystem evidence of that edit. Protecting it needs editor cooperation outside this accepted V1 protocol. For saved changes, recheck disk identity/hash and ownership immediately before a Grace-owned replace. Do not overclaim protection against every uncooperative writer interleaving between a check and an atomic filesystem operation.

**Accepted local schema:** keep the existing shared root exclusion and WDU mechanics; do not add Library as a fourth Branch/Watch/Connect target. The delivered client uses three Library-owned tables: repository state (including the complete bounded catalog), materialized item ancestry, and durable pending/terminal operations. Fetch fresh slot expectations when a local operation needs them instead of persisting a mirror of every vacant server slot, and keep compact conflict provenance on the ordinary conflict item/its pending operation rather than a permanent `library_conflicts` workflow table. This design replaces revision 0.32's six-table design. PR #1044 remains preserved historical source material.

Keep three kinds of local data: repository progress and participation; each item’s last materialized base; and typed operations for saved files, directory creation, explicit rename, incoming changes and baseline installation. An operation stores its generated identity, selected catalog, age and one typed intent/progress value. Its SQL direction, completion and echo indexes derive from that value. Preparation carries its exact predecessor, ancestry and target observation only after acceptance or baseline selection. Baseline tombstones complete without a filesystem checkpoint or fabricated feed change. Once the filesystem change has been checked, one SQLite transaction updates the item, operation and cursor under exact-record guards.

The owner accepted the [local type and saved-content redesign](https://github.com/ScottArbeit/Grace/issues/1073#issuecomment-5594043263) on 2026-09-08, following an [18-case real Windows/SQLite object experiment](design/Libraries.Object-Experiment.md). Saved-file intent refers to complete immutable content in the configured existing object directory, normally `.grace/objects`. Capture holds a stable source reader, streams into a same-volume temporary object, flushes, hashes and publishes without replacing an existing object, verifies the final object, and only then commits the reference. Size, SHA-256, BLAKE3 and the original object locator remain frozen across working-file changes and rename. Upload reads that verified object. A later save becomes a distinct operation with its actual materialized base. Restart discovers a committed capture from SQLite and content identity without a caller-held operation ID.

Missing or corrupt referenced content blocks; newer working bytes cannot repair an older operation or its frozen request. Rejected saved-file work retains its reference and request. Existing metadata cleanup and bounded terminal-operation pruning do not delete these shared physical objects; this change adds no reference-count table or retention lifecycle. Saved-content capture, hashing, comparison and upload are streamed. The existing incoming retained-content download and publication still buffer bytes, so this is not an end-to-end bounded-memory claim.

For initial onboarding, repository state adds an embedded `BaselineSelection` with bootstrap identity, selected boundary, metadata-complete and boundary-applied flags. `NextPageToken` belongs to acquisition until installation finishes, then to accepted-change paging. `BaselineItem` in an operation retains selected metadata independently from its optional genuine `Accepted` change. Baseline work is not a fabricated server operation. There are still exactly three tables and no additional server owner.

Persist each page and its continuation in one transaction before any Library content effects. Resolve the complete live graph after the final page, then install parents before children. Tombstones complete as no-effect work without resolving historical parents. Persist preparation before publication, verify selected bytes with BLAKE3, SHA-256 and size, then commit the live item and terminal work without moving the applied cursor. Verify every required completed result before a separate transaction makes the selected boundary applied. Only the subsequent complete accepted-change pull releases saved-file capture.

An incomplete acquisition can replace its selection after HTTP 410 only while the local root remains empty and the catalog unchanged. Complete metadata keeps its exact selected revisions after token expiry. An unprepared occupied target blocks even when bytes match; a prepared empty directory may resume, but new children block completion. Changed completed content or parents prevent false boundary completion. Local state and current catalog are rechecked before affected effects and completion under the existing root lease. These are point-in-time checks, with no stronger guarantee against uncooperative filesystem writers.

The [baseline experiment](design/Libraries.Baseline-Experiment.md) records the accepted 46-case Windows/SQLite result and its modeled remote limits. Production tests exercise these transaction and filesystem boundaries; the hosted populated-A/new-B fixture uses actual APIs and CLI processes. Ordinary interruption/restart evidence does not establish power-loss durability or a live Watch/SignalR lifetime.

For an incoming file rename, changed old-path bytes may be removed only when those exact nonempty bytes are already accepted and retained by an existing local operation. Reread that operation and the source immediately before removal. A distinct save at the prepared destination keeps the original item and materialized revision; it does not become an unrelated create. If the server deleted the item before its local edit was submitted, retain the `ItemTombstoned` rejection, saved source and exact request without resurrection. An excluded zero-byte source or target prevents the affected filesystem change and cursor completion.

## Additive catalog adoption: accepted, not implemented

**Readiness: Plan-ready for implementation planning of LIB-019 through LIB-021.** This assessment combines the [accepted D1-D3 decisions](https://github.com/ScottArbeit/Grace/issues/1037#issuecomment-5610931795), [bounded experiment](design/Libraries.Catalog-Adoption-Experiment.md), current source at `9b18c97ab342d319d3bdeaedc5f1d64571913cf5`, and the [production acceptance mapping](design/Libraries.Catalog-Adoption-Validation.md). It does not certify a production adoption command. Each implementation issue still needs its own readiness gate and fresh base assessment.

The benefit is adding a second Library root without discarding an existing copy's materialized items or onboarding again. Keep the delivered onboarding, explicit file rename, typed operation model, `Common.ItemKind`, verified saved objects, rejection/resume, durable pause and GUID-backed `LibraryCursorEpoch`. `AppliedCursor` remains an opaque signed token. Participation/progress DUs and a local AppliedCursor wrapper are unaccepted recommendations and remain excluded.

### Accepted scope

- **D1:** two already onboarded Windows 11 copies of one repository; one existing root becomes exactly two through one direct catalog successor. Preserve the original root. The added path is normalized and non-overlapping, and its local directory already exists, is ordinary and empty. The added Library may contain remote changes if the retained feed covers them.
- **D2:** adoption is explicit and local to each copy. Require completed onboarding, durable pause, no unfinished operation, no partial page token, and no unrecorded local changes or obstructions. Preserve working-copy identity, materialized items and edit bases, typed operation JSON, saved objects, terminal/echo history and pause. Frozen requests are never rewritten. Restart Watch after adoption; only explicit resume clears pause.
- **D3:** retain the exact applied cursor and GUID epoch. Adoption itself applies no feed item and advances no cursor. Resume applies unchanged-root backlog accepted under the old catalog and content accepted in the added root. Unsupported deltas, changed epoch, unavailable history and rebaseline retain state and stop.

Removal, relocation, replacement of the original root, skipped catalog successors, existing-file reconciliation, automatic adoption/rebaseline, fresh multi-root onboarding, stronger cross-domain reservations and other platforms are outside this slice. No production-data migration is needed or implied.

### Command and visible result

Recommended implementation defaults are `grace library sync adopt-catalog` and the existing `LibrarySynchronizationStatus` output shape. These are naming and adapter recommendations, not additional accepted product semantics. The command selects the current server catalog; it does not accept an arbitrary replacement catalog or create a server catalog change. Catalog administration remains a separate existing operation. Use existing repository-scoped read permissions; do not require catalog-admin permission merely to adopt an already configured root locally.

A successful result reports the adopted catalog with `Enabled=true`, `Paused=true`, the retained cursor/epoch and unchanged progress. Human output must explain that Watch needs restarting and explicit resume is still required. Catalog adoption must not report that all remote changes are applied. Refusal or cancellation before commit is nonzero and retains local state and bytes, with a useful explanation through the existing command error convention. An interrupted response after commit is resolved by rereading the row; repeating the same current selection has no additional effects. Resume retains its delivered active-before-synchronization behavior, including active/blocked status on failure.

### Reads, local commit and replay

1. Acquire the existing cancellable root lease. Reread completed, paused repository state and operations. Compare disk with durable materialized items and retained completed application evidence; reject unrecorded input, zero-byte obstructions and unsupported reparse ancestry. Do not capture, upload, delete or reconcile files during adoption.
1. Read the current repository catalog and changes available from the retained signed cursor through existing authenticated APIs. Require the unchanged original root, exactly one added ordinary empty local root, direct predecessor catalog, unchanged epoch and available history. Downloaded feed metadata is not applied work.
1. Immediately before committing, reread the server catalog and recheck the complete local row, operations and relevant physical observations under the lease. A changed input prevents the local update. Catalog reads retain the accepted point-in-time semantics; they do not reserve version-control publication.
1. In one SQLite transaction compare the complete expected repository fields and update only its embedded catalog. Preserve cursor, epoch, pause, lifecycle/progress, paging/baseline fields and working-copy identity. Do not change item/operation rows, saved objects or the three-table schema. After an uncertain outcome, a fresh read identifies either the old selection or the committed new selection.
1. On explicit resume, retain each incoming change's immutable original catalog separately from the operation envelope's selected application catalog. Admit the predecessor-catalog case only within this supported direct additive transition, and reject unsupported history before capture, publication or cursor effects. Local frozen requests keep their exact original catalog and existing completion checks.
1. Use ordinary preparation, byte publication and exact item/operation/cursor completion to replay every genuine feed predecessor. If publication succeeds before SQLite completion, reuse retained operation state and published bytes on restart. Never substitute a baseline boundary, skip old-root backlog or recapture an immutable accepted change.

The prototype demonstrated these existing record fields can represent the two catalog facts. It did not establish a production clean-tree scanner from arbitrary durable state: its expected tree was a verified fixture snapshot. Production must use durable materialization evidence and the existing physical-path checks, with positive clean-tree and negative dirty/obstructed tests. The [validation mapping](design/Libraries.Catalog-Adoption-Validation.md) preserves this obligation rather than treating the fixture snapshot as a production algorithm.

The server's `IsInLibrary` remains a point-in-time classification. Existing Save/Reference/DirectoryVersion owners retain their current behavior. A stale Watch observation queued behind the root lease must reread pause before Library effects. The experiment exercised that actual classifier boundary, not a complete running Watch adoption lifetime or atomic cross-domain exclusion.

### Implementation-planning boundary

Use one Product V1 Tier 2 mainline slice. Its first value-bearing test is actual adoption in A, publication under the new root, then actual adoption/resume in B with old-root backlog still pending. Reuse the existing local-state, operation, filesystem and synchronization modules; command/output registration and shared CLI/hosted test files are likely overlapping write surfaces and belong to one owner. No runtime prerequisite PR or integration branch is justified by the experiment.

Stop for a new durable lifecycle, table, owner, rewritten frozen request, cursor advancement without completed application, required rebaseline, broader root transition, stronger cross-domain guarantee or another material product decision. The easiest overbuild is general catalog reconciliation; the easiest under-test is updating only the catalog row and overlooking the old-catalog completion check. Remaining command wiring and clean-tree validation are production work within this scope, not reasons to reopen D1-D3.
